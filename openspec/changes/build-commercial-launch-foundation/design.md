## Context

项目当前是前端主导的 H5 对局原型，具备基础规则、AI 与界面能力，但缺少商业化上线所需的“系统基础设施”。上线赚钱目标要求我们从单机产品升级为“账号化、数据化、运营化、支付化”的在线产品。核心约束：
- 支付与权益必须具备强一致可追溯能力。
- 用户数据必须可跨设备恢复。
- 线上发布必须支持灰度和快速回滚。
- 活动与任务需支持运营无代码配置。

## Goals / Non-Goals

**Goals:**
- 建立统一的用户身份与云数据体系，支持游客转正。
- 建立订阅与内购主链路，形成可观测的收入漏斗。
- 建立任务/签到/活动/公告系统，支持持续运营。
- 建立埋点监控与发布治理，确保可持续迭代。
- 在不破坏现有对局体验的前提下，增强留存与转化触发点。

**Non-Goals:**
- 本阶段不建设复杂 PVP 匹配与实时联机系统。
- 本阶段不建设大型社区内容审核体系。
- 本阶段不引入跨区域多活部署，先以单区域高可用为目标。

## Decisions

1. 架构拆分为“游戏前端 + 业务后端 + 运营后台”三层。
   - 原因：降低耦合，支持并行开发。
   - 备选：全部前端本地化。放弃原因：无法承载支付、账号、运营系统。

2. 账号体系采用“游客ID + 第三方登录绑定”双轨制。
   - 原因：降低首登门槛并保留转化能力。
   - 备选：强制登录。放弃原因：首日流失风险高。

3. 支付模型采用“订单状态机 + 幂等回调 + 权益发放日志”。
   - 原因：保障资金安全和对账能力。
   - 备选：前端直发放。放弃原因：存在严重安全风险。

4. 运营系统采用配置驱动（任务、活动、奖励规则可热更新）。
   - 原因：提升运营迭代效率。
   - 备选：代码硬编码。放弃原因：发布成本高，响应慢。

5. 埋点治理采用事件字典 + 版本化 schema + 数据质量校验。
   - 原因：确保分析可用与跨版本可比。
   - 备选：自由埋点。放弃原因：后期数据不可用。

6. 上线采用“灰度分流 + 指标阈值自动回滚”。
   - 原因：降低线上事故损失。
   - 备选：全量直发。放弃原因：风险不可控。

## Risks / Trade-offs

- [支付回调异常导致权益未发放] → 引入补单任务与人工补偿工具。
- [埋点口径不一致导致运营误判] → 建立埋点评审和自动校验脚本。
- [活动配置错误引发经济系统失衡] → 配置审批流 + 灰度活动开关。
- [账号绑定失败造成数据丢失] → 绑定前后快照与可回滚映射策略。
- [上线期间性能抖动] → 预压测 + 发布时熔断降级策略。

## Migration Plan

1. 第1阶段：上线账号与云存档（不含支付），验证数据闭环。
2. 第2阶段：上线支付和会员权益，先灰度给小流量用户。
3. 第3阶段：上线运营系统（任务签到活动）并接入数据看板。
4. 第4阶段：完善风控、告警、回滚机制后全量上线。

## Open Questions

- 首版订阅权益优先提供“去广告”还是“高级复盘”？
- 初期支付渠道是先上单渠道（微信/平台内购）还是并行双渠道？
- 活动奖励中的货币体系是否需要拆分免费币与付费币？
- 游客数据最长保留期限与清理策略如何设定？
