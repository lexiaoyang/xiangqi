## Context

当前应用是 Vite + React 的 H5 迷宫战役游戏，已有本地战役存档、体力、金币、商店占位、道具、关卡和结算，但商业化闭环仍停留在前端 mock。要支撑真实运营，需要把“用户身份、资产、支付、广告、奖励和运营配置”从 UI 占位升级为有服务端权威状态、可审计账本、可幂等重试、可跨设备恢复的基础平台。

约束：

- H5 版本需要能在普通浏览器、WebView、小程序/小游戏容器中运行，支付和广告能力必须通过适配层接入。
- 客户端可以离线展示缓存状态，但资产、订单、奖励发放和退款处理必须以服务端为权威。
- 现有 `campaign:save:v1` 不应被破坏；迁移应采用渐进式双写/回填。
- 所有商业化入口必须能远程关闭或降级，避免第三方 SDK、支付渠道、广告填充异常影响核心闯关。
- 用户、支付、广告、奖励必须具备审计日志和幂等键，防止重复发货、重复领奖和回调重放。

## Goals / Non-Goals

**Goals:**

- 建立游客到实名/绑定账号的完整生命周期，支持跨设备云存档和账号恢复。
- 建立统一资产账本，金币、体力、道具、票券等资产所有变更均可追踪。
- 支持商品目录、订单、支付回调、收据校验、发货、退款、补单和对账。
- 支持激励视频、插屏、Banner/原生广告位的频控、冷却、奖励发放和失败降级。
- 支持奖励中心，覆盖签到、任务、成就、邮件、礼包、活动奖励和补偿。
- 支持远程配置、A/B 实验、活动编排、埋点事件和商业化漏斗分析。
- 支持隐私同意、未成年人保护、广告披露、支付二次确认和审计留痕。

**Non-Goals:**

- 不在本变更内选择具体支付服务商或广告聚合 SDK 的最终商务方案。
- 不一次性实现完整运营后台 UI，但会定义后台所需数据合同和 API 边界。
- 不引入强制登录门槛；游客仍应能开始游戏。
- 不把客户端本地存档作为资产最终凭证。
- 不承诺所有第三方渠道同一阶段上线，可先以 Web mock/provider sandbox 实现适配层。

## Decisions

### Decision 1: 服务端权威资产账本

用户资产采用 append-only ledger 事件模型，服务端保存资产快照和资产流水。客户端只能提交意图，例如“领取奖励”“创建订单”“观看广告完成”，最终资产变更由服务端写入账本。

理由：

- 可以审计每一笔金币、体力、道具来源。
- 支持退款扣回、补单、活动补偿和风控回放。
- 比直接改用户资产字段更容易处理并发和幂等。

替代方案：客户端本地直接加币再同步。该方案实现快，但无法防刷、无法可靠退款、跨设备冲突复杂，因此不采用。

### Decision 2: 模块化 provider 适配层

支付和广告通过 provider interface 接入：`PaymentProvider`、`AdProvider`、`AuthProvider`、`AnalyticsProvider`。核心业务只依赖领域接口，不直接依赖 SDK。

理由：

- H5、小游戏、App WebView 的支付/广告 API 差异很大。
- 便于先用 mock/sandbox 验证产品流程，再替换真实渠道。
- SDK 异常时可由 provider 返回标准错误并触发降级。

替代方案：业务代码直接调用具体 SDK。短期快，但后续多渠道维护成本高，不采用。

### Decision 3: 幂等优先的订单与奖励流程

所有会发资产的操作必须包含幂等键：订单号、广告展示 token、奖励领取 id、邮件领取 id、任务进度事件 id。服务端必须对重复请求返回同一结果，不重复发放。

理由：

- 支付回调、广告完成回调、弱网重试天然会重复。
- 幂等是商业化系统的底线，不然后续补救成本极高。

替代方案：仅前端禁用按钮防重复。无法抵御刷新、并发、回调重放，不采用。

### Decision 4: 远程配置驱动商业化入口

商店 SKU、广告位频控、奖励任务、活动礼包、实验分流、入口开关均由远程配置驱动。客户端启动后拉取配置，失败时使用随包默认配置。

理由：

- 商业化需要快速调整，不应每次发版。
- 可按国家/渠道/版本/用户分层调整价格、奖励和广告压力。
- 支持一键下线异常广告位或支付渠道。

替代方案：配置写死在前端。上线快但不可运营，不采用。

### Decision 5: 本地缓存 + 云端快照的渐进迁移

现有 `campaign:save:v1` 保留为离线缓存。登录后上传本地进度，服务端合并为云端快照。资产以服务端账本为准；关卡进度可按最高进度/最好星数合并。

理由：

- 不破坏现有玩家本地数据。
- 游戏可离线进入，但商业化资产需要云端确认。
- 支持游客升级账号时自然迁移。

替代方案：上线后强制清空本地存档。体验不可接受，不采用。

### Decision 6: 合规能力内建，不作为后补

隐私同意、广告披露、支付二次确认、未成年人限制、注销和数据导出入口必须与模块一起设计。商业化入口读取合规状态决定是否展示。

理由：

- 支付和广告合规风险高，后补容易漏。
- 不同渠道审核会要求明确的隐私、广告和支付说明。

替代方案：上线前临时补弹窗。风险高，不采用。

## Risks / Trade-offs

- [Risk] 服务端平台范围大，首期实现周期长 → Mitigation：按 MVP 分阶段，先做 mock provider + 账本 + 奖励中心，再接真实支付/广告。
- [Risk] 资产双写期间本地和云端状态不一致 → Mitigation：资产服务端权威，关卡进度按可合并字段处理，客户端展示同步状态。
- [Risk] 第三方支付/广告 SDK 行为不稳定 → Mitigation：provider 适配层统一错误码、超时、重试和远程开关。
- [Risk] 激励广告奖励被刷 → Mitigation：广告 token 服务端签发，完成回调校验展示 id、过期时间、用户和广告位。
- [Risk] 远程配置错误导致奖励过高或入口不可用 → Mitigation：配置 schema 校验、灰度发布、版本回滚、默认兜底配置。
- [Risk] 隐私/未成年人状态影响商业化展示 → Mitigation：商业化入口统一查询 compliance gate，不在各页面分散判断。

## Migration Plan

1. 新增客户端领域模型和 mock API：用户、资产、订单、广告、奖励、配置。
2. 保留现有本地存档，新增本地缓存命名空间：`platform:user:v1`、`platform:wallet:v1`、`platform:config:v1`。
3. 引入服务端 API mock/sandbox，实现账本、配置和奖励中心最小闭环。
4. 将商店占位改接商品目录和订单状态，将奖励中心入口接入任务/签到/邮件。
5. 引入云存档合并策略，游客升级账号时上传本地进度。
6. 接入广告 provider sandbox，验证激励视频奖励幂等发放。
7. 接入支付 provider sandbox，验证订单、收据校验、发货、退款和补单。
8. 增加远程开关、埋点、错误监控和灰度策略。

Rollback：

- 远程关闭支付、广告、奖励中心入口，回退到当前本地战役体验。
- 保留已写入账本和订单，不删除服务端数据。
- 客户端失败时使用随包默认配置和本地进度缓存。

## Open Questions

- 首期目标渠道是纯 Web、微信小游戏、App WebView 还是多端并行？
- 支付首期使用 IAP、微信支付、支付宝、Stripe，还是先 mock/sandbox？
- 广告首期选择单一 SDK 还是广告聚合？
- 是否需要未成年人实名/防沉迷硬性接入，还是先做年龄声明与商业化限制？
- 运营后台是否在本仓库实现，还是仅定义 API 与配置 JSON？
