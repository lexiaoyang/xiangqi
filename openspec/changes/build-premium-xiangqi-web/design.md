## Context

本次变更目标是构建可长期演进的中国象棋 Web 平台，而不是一次性 Demo。系统需同时满足三类需求：面向普通用户的高品质 UI 体验、面向进阶玩家的高强度 AI 对弈、面向训练与学习场景的推荐走法与复盘分析。核心约束包括：
- 单步决策等待上限 60 秒，超时必须有确定性行为。
- 地狱模式与推荐走法需具备明显高于普通引擎参数的棋力，且推荐链路应在基准对局中稳定压制地狱机器人。
- 前端响应流畅，AI 计算不能阻塞主线程。

## Goals / Non-Goals

**Goals:**
- 建立分层架构：规则引擎、AI 搜索、推荐服务、UI 展示解耦，支持独立优化。
- 提供简单/困难/地狱三档难度，并明确参数与棋力评测标准。
- 提供 1 分钟步时、超时治理、推荐走法与一键采用能力。
- 提供完整对局体验：动画反馈、局势评估、复盘与棋谱导出。
- 建立自动化回归：规则正确性测试、性能基准、AI 对战 ELO 评估。

**Non-Goals:**
- 本阶段不实现多人在线实时对战与赛事系统。
- 本阶段不实现语音讲解、直播互动或社交大厅。
- 本阶段不追求强引擎分布式集群部署，先以单机/单实例可用为目标。

## Decisions

1. 前后端职责划分：前端负责展示、交互与局面回放；AI 决策放在独立计算层（Web Worker 或后端服务）。
   - 原因：避免主线程卡顿，并允许后续替换更强引擎实现。
   - 备选：全部前端同步计算。放弃原因：复杂局面下无法保证流畅与 60 秒稳定响应。

2. AI 分层策略：统一搜索框架（迭代加深 + Alpha-Beta + 置换表），不同难度通过深度、时间预算、候选剪枝和开局库覆盖率调参。
   - 原因：复用核心代码，降低维护成本，同时保证难度可解释。
   - 备选：三套独立引擎。放弃原因：实现与调参成本过高，行为不可控。

3. 推荐走法采用“高于地狱模式”的独立推理配置。
   - 原因：满足“持续使用推荐可稳定压制地狱机器人”的目标，推荐应是教学与辅助上限。
   - 备选：直接复用地狱模式输出。放弃原因：无法形成显著指导价值。

4. 步时机制采用“服务端/引擎时钟为准 + 前端倒计时镜像”。
   - 原因：防止前端计时漂移与作弊篡改，确保超时裁定一致。
   - 备选：纯前端计时。放弃原因：可信度与一致性不足。

5. UI 技术选型：组件库 + 自定义棋盘渲染层 + 动画系统，支持深浅主题与移动端手势优化。
   - 原因：在保证精美度的同时提升开发效率与可维护性。
   - 备选：纯手写所有组件。放弃原因：迭代效率低、视觉一致性风险高。

6. 质量评估策略：引入离线基准局集、地狱模式对抗赛与推荐链路胜率测试，作为发布门槛。
   - 原因：将“顶级体验”目标转化为可验证指标。
   - 备选：仅人工体验验收。放弃原因：主观性强，无法稳定回归。

## Risks / Trade-offs

- [推荐强度不足，无法稳定压制地狱模式] → 建立推荐专用参数集与基准胜率阈值，未达标禁止发布。
- [高难度搜索导致超时或卡顿] → 采用迭代加深与硬超时中断，超时回退次优解并记录指标。
- [规则实现细节错误引发判定异常] → 建立规则单测矩阵（将军、困毙、长将/长捉策略）并引入棋谱回放回归。
- [移动端性能不足影响动画体验] → 降级特效、分级帧率策略、按设备档位动态切换渲染细节。
- [AI 与 UI 模块耦合演进困难] → 强制接口契约化（输入 FEN/局面对象，输出走法与评估），禁止跨层访问内部状态。

## Migration Plan

1. 第一阶段：落地规则引擎、棋盘 UI 与本地简单模式，打通完整单机对局闭环。
2. 第二阶段：接入困难/地狱模式、步时机制与推荐走法，并上线基准评测流水线。
3. 第三阶段：加入复盘分析与棋谱系统，完善可观测性与异常告警。
4. 回滚策略：任何阶段若核心规则或 AI 决策出现严重回归，保留上一个稳定包并关闭高阶能力入口（地狱模式、推荐、复盘）。

## Open Questions

- 地狱模式目标棋力的量化标准采用内部 ELO 还是外部公开引擎对标分？
- 推荐走法是否需要解释文本（如“弃子换先手”）以提升教学价值？
- 超时处理默认采用判负还是托管自动走子，是否按模式区分策略？
- 是否在首版开放“禁用推荐”挑战模式，用于竞技公平和排行榜可信度？
