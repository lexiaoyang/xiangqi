## Context

当前项目已具备战役大厅、账号/钱包、商店、广告 provider、奖励中心、远程配置和合规 mock，但用户在首页无法强感知运营活动、广告激励和音效反馈。现有广告入口只是普通按钮，活动中心缺失，首页没有活动弹窗，音频体验完全为空。这会让产品看起来像工程 Demo，而不是一线小游戏。

约束：

- H5/小游戏环境存在浏览器自动播放限制，背景音乐必须在首次用户交互后启动。
- 广告激励必须清楚标注“看广告”，不能伪装成普通奖励。
- 活动弹窗不能无限打扰，需要频控、优先级和“今日不再提示”。
- 背景音乐、音效、活动弹窗、广告激励必须可由远程配置关闭或降级。
- 当前商业化平台已有 mock provider 和 ledger，新增奖励必须继续通过幂等账本入账。

## Goals / Non-Goals

**Goals:**

- 建立可复用音频系统，支持 BGM、UI SFX、奖励/购买/广告/错误反馈音、静音和音量持久化。
- 建立活动中心，让活动列表、详情、任务、奖励、倒计时和入口状态配置化。
- 建立首页活动弹窗，让用户进入首页即可看到运营活动和广告/奖励/商店转化入口。
- 强化广告激励，让“看广告领体力”和“看广告给提示”成为首页、玩法资源不足、奖励中心、结算页都看得见的标准 offer。
- 建立活动、弹窗、广告、音频相关分析事件，为后续运营调优提供数据。
- 通过项目 skill 固化“一线大厂小游戏”设计标准，后续所有设计都按该标准执行。

**Non-Goals:**

- 不在本变更内接入真实广告 SDK 或真实音频素材版权采购。
- 不实现完整运营后台，只定义前端配置、mock API 和数据合同。
- 不强制所有用户看广告；广告 offer 必须可关闭、可冷却、可降级。
- 不将音频播放作为核心玩法依赖；静音用户必须仍可完整游戏。

## Decisions

### Decision 1: 使用 AudioManager 统一管理 BGM 和 SFX

新增 `AudioManager` 负责加载、播放、暂停、音量、静音、首次交互解锁和状态持久化。UI 不直接创建 `Audio` 对象，只调用 `playSfx("reward_claim")`、`playBgm("lobby")` 等语义方法。

理由：

- 浏览器自动播放限制需要集中处理。
- 多页面、多弹窗、多广告回调都可能触发音效，分散实现会冲突。
- 后续替换真实素材、分渠道关闭音频、接小游戏音频 API 更容易。

替代方案：在每个按钮里直接 new Audio。实现快，但难以统一静音、音量、解锁和降级，不采用。

### Decision 2: 活动中心由 RemoteConfig 驱动

活动中心读取 `events` 配置，包含活动 id、标题、视觉主题、时间窗、入口图、任务、奖励、CTA、目标人群和优先级。客户端使用 bundled default config，远程失败时展示缓存但阻止需要服务端确认的新领取。

理由：

- 活动是运营核心，必须不发版可调整。
- 首页弹窗、奖励中心、广告 offer 都要引用活动配置。
- 后续可按渠道、进度、付费状态做活动分层。

替代方案：活动写死在组件里。短期快，但无法运营，不采用。

### Decision 3: 首页活动弹窗使用独立展示队列

新增 popup queue：从远程配置筛选当前可展示弹窗，按优先级排序，检查用户频控记录，展示最高优先级弹窗。弹窗关闭、点击、今日不再提示都写入本地缓存并打点。

理由：

- 首页可能同时有签到、首充、广告补给、活动、公告等弹窗，必须有仲裁。
- 没有频控会破坏留存体验。
- 弹窗是商业化转化入口，需要完整漏斗数据。

替代方案：每个模块自己弹窗。会造成多弹窗叠加和体验失控，不采用。

### Decision 4: 广告激励使用 Offer 模型而不是单一按钮

广告入口统一抽象为 `RewardedAdOffer`：placement、奖励内容、触发场景、冷却、每日上限、文案、图标、CTA、可用状态、失败原因。首页、体力不足、提示不足、奖励中心和结算页复用同一 offer 渲染。

理由：

- “看广告领体力”和“看广告给提示”是不同场景但流程相同。
- Offer 可配置化，便于运营调整奖励和展示压力。
- 可统一处理冷却、次数限制、pending reward retry 和到账提示。

替代方案：在每个页面写独立广告按钮。重复逻辑多，频控和文案难一致，不采用。

### Decision 5: 大厂小游戏体验标准内建到技能

新增项目 skill `tier-one-mini-game-standard`，规定后续所有 UI/UX、活动、广告、音效、商业化、动效、文案和测试都必须按一线小游戏标准审视。

理由：

- 避免继续产出工程占位或“白卡片堆功能”。
- 让后续 agent 在需求、OpenSpec、实现、评审时自动引用同一标准。
- 把主观“好看”转成可执行检查项。

替代方案：只在本次任务里口头要求。上下文会丢失，不采用。

## Risks / Trade-offs

- [Risk] 音频自动播放失败 → Mitigation：首次点击任意主按钮后解锁，失败时静默降级并提示音频关闭状态。
- [Risk] 活动弹窗过度打扰 → Mitigation：优先级队列、每日展示上限、今日不再提示、紧急 kill switch。
- [Risk] 广告入口看不见或像普通按钮 → Mitigation：统一使用广告标签、奖励预览、视频图标和高对比 offer card。
- [Risk] 广告完成后网络失败导致奖励丢失 → Mitigation：pending show token 本地缓存，重试到过期；服务端幂等发放。
- [Risk] 音效素材增加包体 → Mitigation：首期使用轻量短音频或合成音 fallback，素材按需懒加载。
- [Risk] 活动配置错误导致奖励过高 → Mitigation：schema 校验、默认上限、配置回滚、kill switch。

## Migration Plan

1. 新增音频配置、音频缓存键和 `AudioManager`，默认静音/低音量策略可配置。
2. 新增活动配置 schema 和 bundled default events。
3. 新增活动中心 screen、首页入口和活动详情/任务/奖励 UI。
4. 新增首页活动弹窗队列和展示记录缓存。
5. 新增 rewarded ad offer registry，接入首页、体力不足、提示不足、奖励中心和结算页。
6. 扩展 mock provider/server，支持活动配置、弹窗记录、活动奖励、广告提示奖励。
7. 补分析事件和测试。
8. 新增项目 skill，并在后续实现/评审中使用。

Rollback：

- 远程关闭 `events`、`homePopups`、`audio` 或对应 ad offer。
- 保留已领取奖励账本，不删除历史数据。
- 弹窗或音频异常时降级为无弹窗/静音但不影响核心闯关。

- 首页弹窗默认是否每天只展示一次，还是按活动类型分别频控？
- 看广告给提示的 hint 发放是否进入平台 wallet，还是同步到现有 `CampaignSaveV1.toolsUnlocked`/道具计数？
