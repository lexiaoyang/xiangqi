## Context

支付订单状态机涉及客户端、账号/业务服务与运营后台协同，属于跨模块变更。当前相关流程存在口径不一致、异常恢复能力弱、可观测性不足等问题，需要在实现前统一技术决策与边界。

## Goals / Non-Goals

**Goals:**
- 同一订单在任意时刻仅有一个合法状态。
- 重复回调不引发重复发货或重复记账。
- 异常订单可自动或人工闭环。

**Non-Goals:**
- 不重构第三方支付 SDK。
- 不实现跨渠道统一退款编排。

## Decisions

- 状态机采用事件溯源日志 + 当前态快照双写方案。
- 回调处理以 order_id + provider_event_id 实现幂等。
- 超时订单由调度任务迁移到 CLOSED_TIMEOUT 并记录原因。

## Risks / Trade-offs

- [第三方回调乱序] → 通过状态版本号和事件时间戳拒绝旧事件。
- [状态迁移遗漏] → 引入迁移白名单与单元测试覆盖全部路径。
- [对账差异增加] → 每日自动对账并对差异单发起补偿。
